# Specification Guidelines

## Назначение

Этот гайдлайн описывает правила написания спецификаций — документов, которые определяют **что** должна делать система, а не **как**. Спецификации используются AI-агентами и разработчиками для реализации, тестирования и аудита.

---

## 1. Структура спецификации

Каждая спецификация находится в `specs/{domain}/{spec-id}-spec.md`.

### 1.1 Обязательные секции

```markdown
# {spec-id}-spec — {Название}

## Purpose
{Что и зачем делает функциональность. 1-2 предложения.}

## Preconditions
{Условия, необходимые для выполнения.}

## Inputs
{Входные данные и ограничения.}

## Behavior
{Подробное описание ожидаемого поведения.}

## Business rules
{Правила и ограничения.}

## Errors
{Ситуации, вызывающие ошибки/исключения, и реакция системы.}

## Acceptance criteria
{- [ ] {Проверяемый критерий}}
```

**Все секции обязательны**, кроме необязательных (указаны ниже). Если секция неприменима — пропускай её полностью, не оставляй пустой.

### 1.2 Необязательные секции

```markdown
## Examples
{Примеры использования, если они помогают устранить неоднозначность.}

## Changes from previous version
{Если это обновление существующей спецификации.}

### Добавлено
- {что добавлено}

### Изменено
- {что изменено: было → стало}

### Удалено
- {что удалено}
```

## 2. Идентификация спецификаций

### 2.1 Формат ID

```
{domain}-{feature}-spec
```

- `domain` — домен/модуль (kebab-case): `http-client`, `logger`, `auth`
- `feature` — краткое описание функциональности (kebab-case): `cookie-management`, `file-appender`
- Пример: `http-cookies-spec`, `logger-file-appender-spec`

### 2.2 Расположение файлов

```
specs/
├── README.md                        # Каталог спецификаций по доменам
├── http-client/
│   ├── README.md                    # Обзор спецификаций http-client
│   ├── http-client-spec.md          # Основной HTTP-клиент
│   ├── http-cookies-spec.md         # Управление cookie
│   └── http-interceptors-spec.md    # Интерсепторы
├── logger/
│   ├── logger-file-appender-spec.md
│   └── logger-log-service-spec.md
└── ...
```

### 2.3 Связанные спецификации

Каждая спецификация может ссылаться на другие:

```markdown
## Related specs
- [`http-client-spec`](../http-client/http-client-spec.md) — базовый HTTP-клиент
- [`logger-spec`](../logger/logger-spec.md) — логирование запросов
```

## 3. Правила написания

### 3.1 Поведение, а не реализация

**Спецификация описывает ЧТО, а не КАК.**

| ❌ Плохо (реализация) | ✅ Хорошо (поведение) |
|---|---|
| `HttpClientImpl` расширяет `AbstractHttpClient` | Клиент поддерживает GET и POST запросы |
| Используется `Jackson ObjectMapper` с `JavaTimeModule` | Даты десериализуются в ISO-8601 формат |
| Метод вызывает `httpClient.send(request, handler)` | Запрос отправляется синхронно, ответ возвращается блокирующе |

### 3.2 Однозначные формулировки

Используй только проверяемые формулировки:

| ✅ Допустимо | ❌ Недопустимо |
|---|---|
| `должен`, `обязан` | `обычно`, `как правило` |
| `не должен` | `в большинстве случаев` |
| `может` (опционально) | `по возможности` |
| `возвращает` | `возвращает примерно` |
| `бросает {Exception}` | `обрабатывает ошибки` |

### 3.3 Проверяемость

Каждое требование должно быть проверяемым:

| ❌ Не проверяемо | ✅ Проверяемо |
|---|---|
| "Клиент работает хорошо" | "GET запрос возвращает status code 200 для валидного URL" |
| "Ошибки обрабатываются правильно" | "При недоступности сервера бросается `ConnectionException`" |
| "Быстрая обработка" | "Время ответа не превышает 5 секунд при нагрузке до 100 req/s" |

### 3.4 NEEDS_CLARIFICATION

Если требование неясно — **не додумывай**, используй `NEEDS_CLARIFICATION`:

```markdown
## Behavior

### Обработка таймаутов
1. Если сервер не отвечает в течение {NEEDS_CLARIFICATION: таймаут в миллисекундах} мс:
   - Бросается `TimeoutException`
   - Запрос помечается как отменённый
```

**Правила:**
- `NEEDS_CLARIFICATION` — только в секциях `Behavior`, `Business rules`, `Inputs`
- Не используй в `Acceptance criteria` — критерии должны быть однозначными
- Указывай конкретный вопрос в фигурных скобках

## 4. Описание секций

### 4.1 Purpose

**Назначение:** Зачем нужна функциональность? Какую бизнес-проблему решает?

**Правила:**
- 1-2 предложения
- Описывай ценность, а не механизм
- Не упоминай технологии или классы

### 4.2 Preconditions

**Назначение:** Что должно быть истинно перед использованием?

**Что включать:**
- Доступность зависимых модулей/сервисов
- Конфигурационные требования
- Состояние системы
- Авторизация/аутентификация (если нужно)

### 4.3 Inputs

**Назначение:** Какие данные принимаются?

**Формат:**

```markdown
## Inputs

### {Сущность 1}

| Поле | Тип | Обязательное | По умолчанию | Описание |
|---|---|---|---|---|
| `field` | `Type` | Да | — | Описание |

### {Сущность 2}
...
```

**Правила:**
- Указывай типы данных
- Отмечай обязательные поля
- Указывай значения по умолчанию
- Описывай ограничения (максимальная длина, диапазон)

### 4.4 Behavior

**Назначение:** Что происходит при использовании?

**Формат:**

```markdown
## Behavior

### {Сценарий 1}

1. {Шаг 1}
2. {Шаг 2}
3. {Шаг 3}

### {Сценарий 2}
...
```

**Правила:**
- Нумерованные шаги для каждого сценария
- Описывай порядок действий
- Указывай условия (если X, то Y)
- Описывай побочные эффекты
- Для каждого сценария — заголовок

### 4.5 Business rules

**Назначение:** Ограничения и правила, которые система должна соблюдать.

**Формат:**

```markdown
## Business rules

- {Правило 1}
- {Правило 2}
```

**Правила:**
- Каждое правило — отдельный пункт
- Используй "должен", "не должен", "может"
- Указывай константы, диапазоны, значения по умолчанию

### 4.6 Errors

**Назначение:** Ситуации, вызывающие ошибки, и реакция системы.

**Формат:**

```markdown
## Errors

| Ситуация | Исключение/Ошибка | Поведение |
|---|---|---|
| {Описание ситуации} | `{ExceptionType}` | {Что происходит} |
```

**Правила:**
- Описывай ситуацию, а не код
- Указывай тип исключения/ошибки
- Описывай поведение системы после ошибки (продолжает работу / останавливается / откатывает)

### 4.7 Acceptance criteria

**Назначение:** Проверяемые критерии завершения.

**Формат:**

```markdown
## Acceptance criteria

- [ ] {Критерий 1}
- [ ] {Критерий 2}
```

**Правила:**
- Каждый критерий — проверяемое утверждение
- Используй чек-лист формат `- [ ]`
- Критерий должен быть однозначным
- Покрытие: основной сценарий, ошибки, граничные случаи
- НЕ используй `NEEDS_CLARIFICATION` здесь

---

## 5. Обновление спецификаций

### 5.1 Формат изменений

Если спецификация обновляется, добавляй секцию:

```markdown
## Changes from previous version

### Добавлено
- {что добавлено}

### Изменено
- {что изменено: было → стало}

### Удалено
- {что удалено}
```

### 5.2 Проверка на противоречия

При обновлении проверяй:
- Нет ли противоречий с другими спецификациями
- Нужно ли обновить связанные specs
- Не изменился ли контекст (preconditions, зависимости)

---

## 6. Чек-лист качества

Перед предоставлением спецификации на утверждение:

- [ ] ID сформирован правильно ({domain}-{feature}-spec)
- [ ] Purpose описывает ценность, а не реализацию
- [ ] Нет деталей реализации (классы, фреймворки, библиотеки)
- [ ] Все формулировки однозначны (нет "обычно", "как правило")
- [ ] Каждое требование проверяемо
- [ ] Acceptance criteria покрывают основные сценарии
- [ ] Acceptance criteria покрывают ошибки и граничные случаи
- [ ] Нет допущений, выданных за требования
- [ ] NEEDS_CLARIFICATION указаны только где нужно
- [ ] Связанные спецификации указаны
- [ ] Секции необязательные пропущены, если неприменимы
- [ ] Файл ≤ 200 строк (если больше — разбей)

## 7. Примеры

### 7.1 Хорошая спецификация

```markdown
# logger-file-appender-spec — File Appender

## Purpose

Файловый аппендер для записи логов в файл с поддержкой ротации по дате.
Позволяет сохранять логи в файловую систему с настраиваемым форматом и кодировкой.

## Preconditions

- Модуль логирования подключён и инициализирован
- Свойство `logger.file.enabled=true` установлено в конфигурации
- Директория для логов доступна для записи (`logger.file.dir`)

## Inputs

### Конфигурация

| Свойство | Тип | По умолчанию | Описание |
|---|---|---|---|
| `dir` | `String` | `./logs` | Директория для хранения логов |
| `filename-pattern` | `String` | `app-{date}_{timestamp}.log` | Шаблон имени файла |
| `buffer-size` | `int` | `8192` | Размер буфера записи в байтах |

## Behavior

### Создание файла

1. При первом вызове `append(event)`:
   - Формируется имя файла по `filename-pattern`
   - `{date}` заменяется на текущую дату по `date-pattern`
   - Создаётся файл с указанной `encoding`
   - Открывается буферизованный writer

2. При последующих вызовах:
   - Событие записывается в открытый файл
   - При заполнении буфера он сбрасывается

### Ротация файлов

1. При создании нового файла проверяется текущая дата
2. Если дата изменилась с момента последнего создания:
   - Текущий файл закрывается
   - Создаётся новый файл с датой в имени

## Business rules

- Файл создаётся только при первом событии, не при инициализации
- Если `dir` не существует — создаётся автоматически
- Если `dir` недоступен для записи — бросается `LoggerAppenderException`
- `buffer-size` должен быть > 0, иначе бросается `LoggerAppenderException`

## Errors

| Ситуация | Исключение | Поведение |
|---|---|---|
| Директория недоступна для записи | `LoggerAppenderException` | Файл не создаётся, событие не записывается |
| `buffer-size <= 0` | `LoggerAppenderException` | Исключение бросается при создании аппендера |
| Ошибка записи в файл | `LoggerAppenderException` | Ошибка логируется, обработка продолжается |

## Acceptance criteria

- [ ] Файл создаётся при первом событии логирования
- [ ] Имя файла формируется по шаблону с датой и timestamp
- [ ] Директория создаётся автоматически, если не существует
- [ ] События записываются в файл с указанной кодировкой
- [ ] Ротация происходит при смене даты
- [ ] Ошибка записи логируется, обработка продолжается
- [ ] `buffer-size` влияет на размер буфера записи
```

### 7.2 Плохая спецификация

```markdown
# Bad Spec

## Описание
HTTP-клиент для работы с API.

## Поведение
Делает запросы к серверу и возвращает ответ. Обычно работает корректно,
если сервер доступен.

## Критерии
- Клиент работает хорошо
- Ошибки обрабатываются правильно
```

**Почему плохо:**
- Нет чёткого описания поведения
- Нет входных данных и ограничений
- Нет конкретных ошибок и исключений
- Критерии не проверяемые
- Нет business rules
- "Обычно", "хорошо", "правильно" — неопределённые формулировки

### 7.3 Спецификация с описанием реализации (плохо)

```markdown
# Bad Spec — Реализация

## Purpose
Клиент, который использует встроенный HTTP-клиент и JSON-библиотеку для десериализации.

## Implementation
1. `HttpClientImpl` расширяет `AbstractHttpClient`
2. В конструкторе создаётся сериализатор с настройками времени
3. Метод `execute()` вызывает `httpClient.send(request, responseHandler)`
4. Ответ обрабатывается через `ResponseHandler.ofString()`

## Dependencies
- `http-client-library`
- `json-serializer`
- `logging-framework`
```

**Почему плохо:**
- Описывает **как**, а не **что**
- Упоминает классы, методы, фреймворки
- Спецификация должна быть независима от реализации
- Это документация к коду, а не спецификация поведения
