# GIGACODE.md Guidelines

## Назначение

Этот гайдлайн описывает правила создания, наполнения и обновления файла `GIGACODE.md` — центрального документа проекта, который задаёт **контекст для AI-агентов** при работе с репозиторием.

`GIGACODE.md` — это точка входа: агент читает его первым и на основе его содержания определяет структуру проекта, доступные инструменты (скиллы) и навигацию по документации.

---

## 1. Структура файла

Файл состоит из трёх обязательных секций:

```markdown
---
last_updated: YYYY-MM-DD
scope: project
---

# {Название проекта}

## Назначение

{1-2 предложения: что это за проект, какой подход используется.}

---

## Основные каталоги

| Каталог | Назначение |
|---|---|
| `specs/` | ... |
| `docs/` | ... |
| `guidelines/` | ... |
| ... |

---

## Доступные скиллы

| Скилл | Назначение |
|---|---|
| `spec-edit` | ... |
| `spec-impl` | ... |
| ... |
```

### 1.1 Фронтматтер

```yaml
---
last_updated: YYYY-MM-DD
scope: project
---
```

- `last_updated` — дата последнего изменения файла (формат `YYYY-MM-DD`). Обновляется при каждой правке.
- `scope` — всегда `project`.

### 1.2 Секция «Назначение»

- Максимум 2-3 предложения
- Описывай **подход** и **концепцию**, а не технологии
- Пример: «Шаблон для быстрого старта проектов с **SpecDriven** подходом — разработкой, управляемой спецификациями.»

### 1.3 Секция «Основные каталоги»

Таблица из двух колонок: `каталог` → `назначение`.

**Что включать:**
- Все ключевые каталоги верхнего уровня и вложенные (если они несут смысловую нагрузку)
- `specs/` — с указанием формата именования файлов
- `docs/` — с разбивкой по подкаталогам (`architecture.md`, `modules/`, `packages/`, `testing/`)
- `guidelines/` — с перечислением файлов-гайдлайнов

**Правила:**
- Только каталоги, которые агент может использовать как точки входа
- Не включай каталоги с временными файлами, артефактами сборки, node_modules и т.д.
- Для вложенных каталогов указывай полный путь: `docs/modules/`, `docs/packages/`

### 1.4 Секция «Доступные скиллы»

Таблица из двух колонок: `скилл` → `назначение`.

**Что включать:**
- Только скиллы, которые доступны в `.gigacode/skills/` или `.gigacode_vsc/skills/`
- Краткое описание назначения каждого скилла (1 предложение)

**Правила:**
- Сортируй по алфавиту или по значимости
- Не включай скиллы, которые не существуют физически
- Если скилл удалён — удали строку из таблицы

## 2. Правила наполнения

### 2.1 Что НЕ включать

| Не включать | Почему |
|---|---|
| Детали реализации | Это в `docs/` |
| Полные листинги кода | Это в исходниках |
| Инструкции по ручным операциям | Это в `docs/` |
| Историю изменений | Это в git log |
| Зависимости сборки | Это в `package.json` / `pom.xml` и т.д. |
| Конфигурацию IDE | Это в `.idea/` / `.vscode/` |

- GIGACODE.md — **оглавление**, а не справочник

## 3. Обновление

### 3.1 Триггеры

Обновляй `GIGACODE.md` при:

| Триггер | Действие |
|---|---|
| Добавлен новый каталог со смысловой нагрузкой | Добавь строку в таблицу «Основные каталоги» |
| Удалён каталог | Удали строку из таблицы |
| Добавлен новый скилл | Добавь строку в таблицу «Доступные скиллы» |
| Удалён скилл | Удали строку из таблицы |
| Изменилась структура `specs/` | Обнови формат именования в описании |
| Изменилась структура `docs/` | Обнови таблицу каталогов |
| Добавлен новый гайдлайн | Добавь строку в таблицу каталогов |

### 3.2 Порядок действий

1. Определи, какая секция затронута
2. Внеси изменение в таблицу
3. Обнови `last_updated` во фронтматтере
4. Проверь, что файл не превысил 100 строк

### 3.3 Первичная инициализация

Если `GIGACODE.md` содержит шаблонное название (например, `SpecDriven Project Template`) — это признак того, что файл не инициализирован для конкретного проекта.

**Действия при первичной инициализации:**

1. **Проанализируй код проекта** — изучи структуру, зависимости, основные модули, `package.json` / `pom.xml` / `Cargo.toml` и т.д.
2. **Сгенерируй название проекта** — на основе анализа кода и структуры придумай осмысленное название (не шаблонное)
3. **Напиши описание** — 1-2 предложения, отражающие суть проекта и его назначение
4. **Заполни все секции** — каталоги, скиллы, по актуальной структуре

**Пример:**

| Было (шаблон) | Стало (реальный проект) |
|---|---|
| `# SpecDriven Project Template` | `# WebFetch MCP Server` |
| `Шаблон для быстрого старта...` | `MCP-сервер для веб-скрейпинга и извлечения контента из веб-страниц.` |

**Правила:**
- Название должно быть уникальным и отражать суть проекта
- Описание должно отвечать на вопрос «что это и зачем», а не «как сделано»
- Не используй технологии в названии (кроме случаев, когда технология — суть проекта)
- После первичной инициализации файл считается «живым» и обновляется по правилам секции 3.1

### 3.4 Что НЕ требует обновления GIGACODE.md

- Изменение содержимого файлов внутри каталогов (если структура не изменилась)
- Обновление гайдлайнов, спецификаций, документации
- Изменение кода, тестов, конфигурации
- Переименование файлов внутри каталогов (если каталог тот же)

## 4. Примеры

### 4.1 Хороший GIGACODE.md

```markdown
---
last_updated: 2026-10-14
scope: project
---

# SpecDriven Project Template

## Назначение

Шаблон для быстрого старта проектов с **SpecDriven** подходом — разработкой, управляемой спецификациями.

---

## Основные каталоги

| Каталог | Назначение |
|---|---|
| `specs/` | Спецификации поведения. Структура: `specs/{domain}/{spec-id}-spec.md` |
| `docs/` | Документация проекта |
| `guidelines/` | Гайдлайны проекта |

---

## Доступные скиллы

| Скилл | Назначение |
|---|---|
| `spec-edit` | Создание и обновление спецификаций |
| `spec-impl` | Реализация кода по спецификации |
```

### 4.2 Плохой GIGACODE.md

```markdown
---
last_updated: 2026-10-14
scope: project
---

# My Project

## Описание

Этот проект использует Spring Boot 3.x, Java 21, Maven для сборки.
Тесты пишутся на JUnit 5 с Mockito. CI/CD настроен через GitHub Actions.

## Зависимости

- spring-boot-starter-web: 3.2.0
- jackson-databind: 2.15.0
- lombok: 1.18.30

## Как запустить

mvn clean install
mvn spring-boot:run


## Команды

- `mvn test` — запустить тесты
- `mvn spotless:apply` — форматирование
- `mvn checkstyle:check` — линтинг
```

**Почему плохо:**
- Описывает технологии и инструменты — это не контекст для AI-агента
- Содержит команды сборки — это в `README.md`
- Перечисляет зависимости — это в `pom.xml`
- Нет структуры каталогов — агент не понимает, где искать
- Нет скиллов — агент не знает, какие инструменты доступны

---

## 5. Связь с другими документами

`GIGACODE.md` ссылается на:

| Документ | Где находится |
|---|---|
| Гайдлайны | `guidelines/*.md` |
| Спецификации | `specs/**/*.md` |
| Документация | `docs/**/*.md` |
| Архитектура | `docs/architecture.md` |

Обратная ссылка (из `docs/README.md`) на `GIGACODE.md` — **обязательна**.

---

## 6. Чек-лист качества

Перед сохранением изменений в `GIGACODE.md`:

- [ ] Фронтматтер с актуальной датой
- [ ] Назначение — 2-3 предложения, без технологий
- [ ] Таблица каталогов отражает фактическую структуру
- [ ] Таблица скиллов содержит только существующие скиллы
- [ ] Нет деталей реализации, команд сборки, зависимостей
- [ ] Нет дублирования информации из `guidelines/` или `docs/`
