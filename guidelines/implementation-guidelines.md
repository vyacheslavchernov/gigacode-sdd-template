# Implementation Guidelines

## Назначение

Этот гайдлайн описывает правила реализации кода на основе спецификаций. Он обеспечивает согласованность между spec, кодом, тестами и документацией.

---

## 1. Общие принципы

### 1.1 Spec — источник истины

Спецификация определяет **что** должна делать система. Код должен строго соответствовать spec:

- Все требования spec должны быть реализованы
- Поведение кода должно совпадать с описанным в spec
- Исключения/ошибки из spec должны бросаться/возникать в коде
- Acceptance criteria должны быть проверяемы тестами

### 1.2 Минимальные изменения

Реализуй **только** то, что требуется spec:

| ✅ Правильно | ❌ Неправильно |
|---|---|
| Добавь метод, описанный в spec | Рефактори соседний метод "на всякий случай" |
| Исправь расхождение с spec | Добавь новую функциональность без spec |
| Добавь тест для нового требования | Измени существующий тест для обхода бага |
| Удали код, удалённый в spec | Добавь "полезные" методы без spec |

### 1.3 Не ломай существующее

При реализации нового spec:
- Существующие тесты должны продолжать проходить
- Существующий публичный API должен оставаться совместимым
- Изменяй поведение только если spec явно требует

---

## 2. Процесс реализации

### 2.1 Перед началом

1. **Прочитай spec полностью** — включая все секции
2. **Изучи связанные спецификации** — они могут определять зависимости
3. **Изучи текущий код** — структура, паттерны, зависимости
4. **Изучи существующие тесты** — что уже покрыто
5. **Определи scope** — какие файлы нужно изменить/создать

### 2.2 Порядок действий

```
1. Новые классы/модули (если нужно)
2. Изменение существующих классов/модулей
3. Тесты для нового кода
4. Обновление существующих тестов (если нужно)
5. Проверка сборки
6. Проверка тестов
7. doc-sync (обновление документации)
8. spec-audit (проверка соответствия)
```

### 2.3 Определение scope

Составь список:
- **Новые файлы** — какие классы/модули нужно создать
- **Изменяемые файлы** — какие классы нужно модифицировать
- **Новые тесты** — какие тесты нужно добавить
- **Изменяемые тесты** — какие тесты нужно обновить

## 3. Правила написания кода

### 3.1 Соответствие spec

Для каждого элемента spec проверь:

| Элемент spec | Проверка |
|---|---|
| Inputs → Публичный API | Классы, интерфейсы, сигнатуры методов соответствуют |
| Behavior → Поведение | Пошаговый алгоритм реализован точно |
| Business rules → Правила | Все ограничения реализованы |
| Errors → Исключения | Все ситуации покрыты, типы исключений совпадают |
| Acceptance criteria | Каждый критерий проверяем тестом |

### 3.2 Coding standards

Следуй конвенциям языка и проекта:
- Именование: согласуется с языковыми конвенциями (camelCase, snake_case и т.д.)
- Структура файлов: соответствует структуре пакетов/модулей
- Документация: публичные классы/функции документированы (документация языка/проекта)
- Исключения: следуй конвенции иерархии ошибок языка
- Зависимости: используй только те, что в `dependencies` проекта

### 3.3 Обработка ошибок

- Все ошибки из spec должны быть реализованы
- Иерархия ошибок должна соответствовать конвенциям проекта
- Ошибки должны содержать понятные сообщения
- Не скрывай ошибки — логируй или бросай дальше

## 4. Тестирование

### 4.1 Покрытие

Каждый значимый requirement spec должен быть покрыт тестом:

| Сценарий | Покрытие |
|---|---|
| Основной сценарий (Behavior) | ✅ Обязательный тест |
| Бизнес-правила и ограничения | ✅ Обязательный тест |
| Ошибки и исключения (Errors) | ✅ Обязательный тест |
| Граничные случаи | ✅ Обязательный тест |

### 4.2 Структура тестов

```
tests/
├── unit/                          # Юнит-тесты
│   ├── {module}/
│   │   ├── {class}-tests.{ext}    # Тесты для класса
│   │   └── ...
│   └── ...
├── integration/                   # Интеграционные тесты
│   └── {scenario}-tests.{ext}
└── ...
```

**Правила:**
- Один тестовый файл — один тестируемый класс/модуль
- Имена тестов описывают сценарий: `test_{scenario}_{expected_behavior}`
- Тесты должны быть изолированными (mock внешних зависимостей)
- Используй параметризованные тесты для граничных случаев

### 4.3 Паттерны тестов

```
1. Arrange — подготовка данных и mock'ов
2. Act — вызов тестируемого метода
3. Assert — проверка результата
```

**Пример (псевдокод):**

```python
def test_get_request_returns_correct_status():
    # Arrange
    client = HttpClientBuilder().build()
    request = Request("GET", "https://example.com")
    
    # Act
    response = client.execute(request)
    
    # Assert
    assert response.status == 200
    assert response.body == expected_data
```

### 4.4 Не ломай существующие тесты

- Не изменяй существующие тесты для обхода бага
- Если тест не проходит — исправляй код, а не тест
- Добавляй новые тесты, не удаляй старые

## 5. Проверка

### 5.1 Перед вызовом downstream skills

Проверь:
- [ ] Реализация соответствует spec (ручная проверка)
- [ ] Все значимые требования покрыты тестами
- [ ] Тесты проходят (запусти тесты проекта)
- [ ] Сборка проходит (запусти команду сборки)
- [ ] Нет NEEDS_CLARIFICATION (или они отмечены явно)
- [ ] Соблюдена архитектура модулей

### 5.2 Команды проверки

```bash
# Сборка
{build-command}

# Тесты
{test-command}

# Для конкретного модуля (если поддерживается)
{build-command} -m {module-name}
{test-command} -m {module-name}
```

## 6. Документация

**ИСПОЛЬЗУЙ СУБ-АГЕНТА** для вызова `doc-sync`.

После реализации запусти суб-агента с командой:

```
doc-sync: обнови документацию для модуля {module-name}
```

**Что обновляется:**
- `docs/modules/{module}.md` — документация модуля
- `docs/packages/{package}/` — документация пакетов
- `README.md` модулей
- `docs/architecture.md` — если изменилась структура

---

## 7. Аудит

**ИСПОЛЬЗУЙ СУБ-АГЕНТА** для вызова `spec-audit`.

После обновления документации запусти суб-агента с командой:

```
spec-audit: аудит спецификаций для {spec-id}
```

**Что проверяется:**
- Код ↔ Спецификация
- Тесты ↔ Спецификация
- Документация ↔ Код + Тесты

## 8. Предоставление решения пользователю

### 8.1 Формат отчёта

```
## Реализация: {spec-id}

### Изменения кода
- `Path/To/Class.{ext}` — {что изменилось}
- `Path/To/NewClass.{ext}` — {создан}
- `Path/To/Tests.{ext}` — {добавлены тесты}

### Документация (doc-sync)
- `docs/modules/{module}.md` — {что обновлено}
- `docs/packages/{package}/` — {что обновлено}

### Аудит (spec-audit)
- Статус: {PASS/WARN/FAIL}
- Расхождений код↔spec: {N}
- Непокрытых acceptance criteria: {N}
- Расхождений docs↔code: {N}

### NEEDS_CLARIFICATION
- {если есть — список}

### Рекомендации
- {что проверить, что уточнить}
```

### 8.2 Не вноси правки самостоятельно

Предоставь решение пользователю на утверждение:
- Список изменений
- Результат doc-sync
- Результат spec-audit
- NEEDS_CLARIFICATION (если есть)
- Рекомендации

## 9. Критерии завершения

- [ ] Реализация соответствует spec
- [ ] Все значимые требования покрыты тестами
- [ ] Тесты проходят
- [ ] Сборка проходит
- [ ] Документация обновлена (запустил doc-sync через суб-агента)
- [ ] Аудит пройден (запустил spec-audit через суб-агента)
- [ ] Решение предоставлено пользователю на утверждение

## 10. Примеры

### 10.1 Хорошая реализация

```
Spec: logger-file-appender-spec
Changes:
- Created: src/appender/FileAppender.{ext}
- Created: tests/unit/FileAppender-tests.{ext}
- Updated: src/appender/AppenderFactory.{ext} — добавлена регистрация FileAppender

Tests:
- test_create_file_on_first_event — основной сценарий
- test_rotation_on_date_change — ротация
- test_error_on_unwritable_dir — ошибка
- test_buffer_size_affects_buffer — граничный случай

Audit: PASS
0 расхождений, 0 непокрытых критериев
```

### 10.2 Плохая реализация

```
Spec: logger-file-appender-spec
Changes:
- Created: src/appender/FileAppender.{ext}
- Изменён: src/appender/AppenderFactory.{ext} — добавлена регистрация
- Изменён: tests/unit/ExistingAppender-tests.{ext} — удалён failing тест

Проблемы:
- Удалён существующий тест (нарушение принципа "не ломай")
- Не покрыт сценарий rotation на date change
- doc-sync не вызван через суб-агента
- spec-audit не вызван через суб-агента
```
