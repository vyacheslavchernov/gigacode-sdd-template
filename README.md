# SpecDriven Project Template

Шаблон для быстрого старта проектов с **SpecDriven** подходом — разработкой, управляемой спецификациями.

> [!IMPORTANT]
> Этот README — часть шаблона. При инициализации нового проекта через команду `инициализируй проект` он будет заменён на специфичный для вашего проекта.

---

## Что такое SpecDriven

SpecDriven — подход, при котором разработка управляется **спецификациями** (spec), а не кодом. Изменение всегда начинается с описания поведения системы, затем следует реализация и аудит соответствия.

**Принципы:**

1. **Spec — источник истины.** Код должен строго соответствовать спецификации.
2. **Spec описывает ЧТО, а не КАК.** Никаких деталей реализации — только поведение.
3. **Каждое требование проверяемо.** Каждый пункт spec должен быть покрыт тестом.
4. **Аудит обязателен.** После реализации — проверка соответствия spec ↔ код ↔ тесты ↔ docs.

## Быстрый старт

### 1. Инициализация проекта

```
инициализируй проект для {описание}
```

Скилл `template-init` задаст уточняющие вопросы (название, язык, инструменты сборки) и создаст структуру проекта:

- `src/` — исходный код
- `tests/` — тесты
- `guidelines/` — гайдлайны (сборка, тестирование, код-стайл)
- `GIGACODE.md` — обновится под ваш проект
- `.gitignore` — расширится под выбранный стек

**После инициализации:**

```bash
# Установи зависимости
{install-command}

# Запусти сборку
{build-command}

# Запусти тесты
{test-command}

# Начни писать первый spec в specs/
```

### 2. Написание спецификации

```
создай спецификацию для {описание функциональности}
```

Скилл `spec-edit`:
1. Определит домен и ID спецификации
2. Задаст уточняющие вопросы по поведению, входным данным, ошибкам
3. Напишет spec по структуре из `guidelines/specification-guidelines.md`
4. Предоставит на утверждение

**Структура спецификации:**

```markdown
# {spec-id}-spec — {Название}

## Purpose
{Что и зачем}

## Preconditions
{Условия}

## Inputs
{Входные данные}

## Behavior
{Поведение}

## Business rules
{Правила}

## Errors
{Ошибки}

## Acceptance criteria
{- [ ] {Проверяемый критерий}}
```

**Правила:**
- Используй однозначные формулировки: `должен`, `не должен`, `может`
- Избегай: `обычно`, `как правило`, `по возможности`
- Если поведение неизвестно — используй `NEEDS_CLARIFICATION`
- Файл: `specs/{domain}/{spec-id}-spec.md`

### 3. Реализация по спецификации

```
реализуй спецификацию {spec-name}
```

Скилл `spec-impl`:
1. Изучит spec, связанные specs, текущий код и тесты
2. Определит scope изменений
3. Реализует код и тесты
4. Вызовет `doc-sync` для обновления документации
5. Вызовет `spec-audit` для проверки соответствия
6. Предоставит отчёт на утверждение

### 4. Аудит соответствия

```
аудит спецификаций для {spec-name}
```

Скилл `spec-audit` проверит:
- Код ↔ Спецификация
- Тесты ↔ Спецификация
- Документация ↔ Код + Тесты

## Структура проекта

| Каталог | Назначение |
|---|---|
| `specs/` | Спецификации поведения. Структура: `specs/{domain}/{spec-id}-spec.md` |
| `src/` | Исходный код |
| `tests/` | Тесты (unit/, integration/) |
| `docs/` | Документация проекта |
| `docs/modules/` | Документация модулей |
| `docs/packages/` | Документация пакетов |
| `guidelines/` | Гайдлайны проекта |
| `.gigacode/skills/` | Скиллы AI-агентов |

---

## Доступные скиллы

| Команда | Скилл | Назначение |
|---|---|---|
| `инициализируй проект` | `template-init` | Создание структуры проекта, гайдлайнов, обновление GIGACODE.md |
| `создай спецификацию` | `spec-edit` | Создание и обновление спецификаций |
| `реализуй спецификацию` | `spec-impl` | Реализация кода по спецификации |
| `аудит спецификаций` | `spec-audit` | Проверка соответствия spec ↔ код ↔ тесты ↔ docs |
| `обнови документацию` | `doc-sync` | Синхронизация документации с кодом |

`doc-sync` и `spec-audit` вызываются через суб-агентов.

---

## Типичный workflow

```
1. Инициализация проекта
   └─> template-init → структура + гайдлайны

2. Написание spec
   └─> spec-edit → specs/{domain}/{spec-id}-spec.md

3. Реализация
   └─> spec-impl → код + тесты → doc-sync → spec-audit

4. Аудит
   └─> spec-audit → отчёт PASS/WARN/FAIL

5. Повторить для следующей функциональности
```
