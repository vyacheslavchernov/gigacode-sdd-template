# Template Init

Интерактивная инициализация нового проекта на базе SpecDriven-шаблона.

## Сценарий

```
инициализируй проект для {описание}
```

1. Задай уточняющие вопросы (см. ниже)
2. Инициализируй структуру проекта
3. Сформируй гайдлайны
4. Обнови GIGACODE.md
5. Предоставь результат пользователю

## Уточняющие вопросы

Задай вопросы **последовательно**, по одному. Жди ответа перед следующим вопросом.

### Вопрос 1: Название проекта

```
Как называется проект?
```

- Ожидаемый формат: kebab-case или camelCase (например: `webfetch`, `my-api-service`)
- Если не указано — предложи сгенерировать на основе описания

### Вопрос 2: Назначение проекта

```
Кратко опиши назначение проекта — что он делает и какую проблему решает?
```

- 1-2 предложения
- Описывай ценность, а не технологии

### Вопрос 3: Язык программирования

```
На каком языке будет писаться проект?
```

Предложи варианты:

| Язык | Версия |
|---|---|
| TypeScript/Node.js | 20+ (LTS) |
| Python | 3.12+ |
| Java | 21+ (LTS) |
| Rust | 1.75+ |
| Go | 1.22+ |

### Вопрос 4: Инструменты сборки

На основе выбранного языка предложи подходящие инструменты:

**TypeScript/Node.js:**
- Сборка: `npm` (Recommended), `yarn`, `pnpm`
- Тесты: `vitest` (Recommended), `jest`
- Форматирование: `prettier` + `eslint`
- HTTP-фреймворк (если web): `express`, `fastify`, `hono`

**Python:**
- Сборка: `uv` (Recommended), `pip`, `poetry`, `pdm`
- Тесты: `pytest` (Recommended)
- Форматирование: `ruff` (Recommended), `black`
- HTTP-фреймворк (если web): `fastapi` (Recommended), `flask`

**Java:**
- Сборка: `Maven` (Recommended), `Gradle`
- Тесты: `JUnit 5` + `Mockito`
- Форматирование: `spotless`
- Фреймворк (если web): `Spring Boot` (Recommended)

**Rust:**
- Сборка: `Cargo` (встроен)
- Тесты: `cargo test` (встроен)
- Форматирование: `rustfmt` + `clippy`

**Go:**
- Сборка: `go mod` (встроен)
- Тесты: `go test` (встроен)
- Форматирование: `gofmt` (встроен)
- HTTP-фреймворк (если web): стандартная библиотека (Recommended)

### Вопрос 5: Дополнительные опции (опционально)

```
Нужно ли добавить:
- CI/CD конфигурацию (GitHub Actions)?
- Dockerfile?
- .gitignore для выбранного стека?
```

## Workflow

### Шаг 1: Сбор требований

Задай вопросы последовательно. Зафиксируй ответы:

```json
{
  "name": "project-name",
  "purpose": "short description",
  "language": "typescript|python|java|rust|go",
  "buildTool": "npm|uv|maven|cargo|go",
  "testFramework": "vitest|pytest|junit|...",
  "formatting": "prettier|ruff|spotless|...",
  "extraOptions": {
    "ci": false,
    "docker": false,
    "gitignore": true
  }
}
```

### Шаг 2: Проверка установленных инструментов

Проверь доступность ключевых инструментов:

```bash
# TypeScript
node --version && npm --version

# Python
python --version && uv --version || pip --version

# Java
java --version && mvn --version || gradle --version

# Rust
rustc --version && cargo --version

# Go
go version
```

**Если инструмент не установлен:**
1. Сообщи пользователю
2. Предложи инструкцию по установке
3. Предложи продолжить без него (с предупреждением) или отменить

### Шаг 3: Инициализация структуры проекта

Создай структуру на основе выбранного стека:

#### TypeScript/Node.js (npm + vitest)

```
project-name/
├── src/
│   ├── index.ts
│   └── ...
├── tests/
│   ├── unit/
│   └── integration/
├── package.json
├── tsconfig.json
├── vitest.config.ts
├── .eslintrc.json
├── .prettierrc
└── .gitignore
```

#### Python (uv + pytest)

```
project-name/
├── src/
│   └── {package_name}/
│       ├── __init__.py
│       └── ...
├── tests/
│   ├── unit/
│   └── integration/
├── pyproject.toml
├── .ruff.toml
└── .gitignore
```

#### Java (Maven + JUnit 5)

```
project-name/
├── src/
│   ├── main/
│   │   └── java/
│   └── test/
│       └── java/
├── pom.xml
└── .gitignore
```

#### Rust (Cargo)

```
project-name/
├── src/
│   └── lib.rs
│   └── main.rs (если binary)
├── tests/
├── Cargo.toml
└── .gitignore
```

#### Go (go mod)

```
project-name/
├── pkg/
├── internal/
├── cmd/
├── tests/
├── go.mod
├── go.sum
└── .gitignore
```

**Правила:**
- Создай минимальный "hello world" файл в `src/` — заглушку, которую можно заменить
- Создай минимальный тестовый файл — заглушку
- `.gitignore` — шаблонный (из существующего), потом расширим под стек

### Шаг 4: Формирование гайдлайнов

Создай два новых файла в `guidelines/`:

#### `guidelines/build-run-tests-guidelines.md`

```yaml
---
last_updated: YYYY-MM-DD
scope: guidelines
---

# Build, Run & Tests Guidelines — {project-name}

## Назначение

Этот гайдлайн описывает команды для сборки, запуска и тестирования проекта {project-name}.

---

## Сборка

```bash
{build-command}
```

### {build-command} — описание

{описание что делает команда}

---

## Запуск

```bash
{run-command}
```

### {run-command} — описание

{описание что делает команда, аргументы, переменные окружения}

---

## Тесты

### Юнит-тесты

```bash
{unit-test-command}
```

### Интеграционные тесты

```bash
{integration-test-command}
```

### Все тесты

```bash
{all-tests-command}
```

---

## Форматирование и линтинг

```bash
{format-command}
{lint-command}
{lint-check-command}
```

---

## CI/CD (если добавлено)

{описание pipeline}

---

## Чек-лист перед коммитом

- [ ] Сборка проходит (`{build-command}`)
- [ ] Все тесты проходят (`{all-test-command}`)
- [ ] Форматирование применено (`{format-command}`)
- [ ] Линтинг чист (`{lint-check-command}`)
```

На основе выбранного языка и инструментов:

```yaml
---
last_updated: YYYY-MM-DD
scope: guidelines
---

# Coding Guidelines — {project-name}

## Назначение

Правила написания кода для проекта {project-name} на {language}.

---

### Файлы и директории

{конвенции именования файлов для выбранного языка}

### Переменные и функции

{конвенции именования для выбранного языка}

### Классы и модули

{конвенции именования классов/модулей для выбранного языка}

## 3. Стиль кода

{ссылка на конфиг форматтера + основные правила}
{примеры: отступы, кавычки, import order, и т.д.}

{рекомендуемые паттерны для выбранного стека}
{разделение на слои: domain, service, repository, controller}

{конвенции обработки ошибок для выбранного языка}

**Заполни шаблоны конкретными значениями** на основе ответов пользователя. Не оставляй `{placeholders}` — подставляй реальные команды и правила.

### Шаг 5: Обновление GIGACODE.md

Прочитай текущий `GIGACODE.md`. Обнови:

1. **Название** — замени шаблонное на реальное
2. **Описание** — сгенерируй 1-2 предложения на основе purpose
3. **Таблица каталогов** — добавь новые гайдлайны:

| Каталог | Назначение |
|---|---|
| `guidelines/build-run-tests-guidelines.md` | Команды сборки, запуска, тестирования |
| `guidelines/coding-guidelines.md` | Правила написания кода для {language} |

4. **Фронтматтер** — обнови `last_updated`

**Правила:**
- Не превыси 40 строк (секция каталогов + скиллы)
- Не удаляй существующие секции
- Не добавляй детали реализации

### Шаг 6: Обновление .gitignore

Если проект требует специфичных игнорируемых файлов (node_modules, .venv, target/, .idea/, etc.) — добавь их в `.gitignore`.

### Шаг 7: Предоставление результата

Предоставь пользователю:

```
## Инициализация проекта: {project-name}

### Конфигурация
- Язык: {language} {version}
- Сборка: {buildTool}
- Тесты: {testFramework}
- Форматирование: {formatting}
- CI/CD: {да/нет}
- Docker: {да/нет}

### Созданные файлы
- `src/index.{ext}` — точка входа
- `tests/unit/` — заглушка теста
- `guidelines/build-run-tests-guidelines.md` — команды сборки/запуска/тестов
- `guidelines/coding-guidelines.md` — правила написания кода
- `GIGACODE.md` — обновлён
- `.gitignore` — {обновлён/расширен}

### Команды
- Сборка: `{build-command}`
- Запуск: `{run-command}`
- Тесты: `{test-command}`
- Форматирование: `{format-command}`

### Следующие шаги
1. Установи зависимости: `{install-command}`
2. Запусти сборку: `{build-command}`
3. Запусти тесты: `{test-command}`
4. Начни писать первый spec в `specs/`
```

## Правила

- **Задавай вопросы последовательно**, по одному
- **Не додумывай** — если пользователь не ответил на вопрос, спроси повторно или предложи вариант по умолчанию
- **Проверяй установленные инструменты** перед инициализацией
- **Предлагай инструкции по установке** если инструмент отсутствует
- **Подставляй реальные значения** в гайдлайны — не оставляй placeholder'ов
- **Не ломай** существующую структуру SpecDriven-шаблона
- **Сохраняй** `specs/`, `docs/`, `.gigacode/` без изменений
