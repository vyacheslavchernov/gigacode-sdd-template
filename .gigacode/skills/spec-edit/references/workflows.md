# Workflows -- Spec Edit

See [SKILL.md](../SKILL.md) -- overview and scenarios.

## Управление статусом

**При создании новой spec:**
- Статус всегда `DRAFT`

**При обновлении существующей spec:**
- Если изменения **существенные** (новые требования, изменение поведения, новые edge cases) — статус `DRAFT`
- Если изменения **косметические** (уточнение формулировок, исправление опечаток, добавление примеров) — статус сохраняется
- Если spec был `IMPLEMENTED_NEED_WORK` и изменения устраняют расхождения — после утверждения статус может быть изменён на `IMPLEMENTED_STABLE` (после аудита)
- Если spec был `IMPLEMENTED_STABLE` и изменения вносят новые требования — статус `DRAFT`

**Вопросы для определения статуса при обновлении:**
- Изменилось ли поведение системы (Behavior)?
- Добавлены ли новые требования, которые не были в spec?
- Изменились ли business rules или ошибки?
- Если да на любой вопрос → статус `DRAFT`

## Уточняющие вопросы

### Для новой спецификации

Задай вопросы по каждому применимому разделу:

**Purpose (цель):**
- Что именно должна делать эта функциональность?
- Зачем она нужна? Какую бизнес-проблему решает?

**Preconditions (предусловия):**
- Какие условия должны быть выполнены перед использованием?
- Какие модули/компоненты должны быть доступны?
- Нужна ли авторизация/аутентификация?

**Inputs (входы):**
- Какие данные принимаются?
- Какие типы, форматы, ограничения?
- Какие данные обязательные, какие опциональные?

**Behavior (поведение):**
- Что происходит при успешном выполнении?
- Что происходит при каждом сценарии использования?
- Какой порядок действий?
- Как обрабатываются edge cases?

**Business rules (правила):**
- Какие ограничения существуют?
- Какие правила валидации?
- Какие зависимости от других систем?

**Errors (ошибки):**
- Какие ошибки возможны?
- Как должны обрабатываться?
- Какие исключения бросаются?

**Acceptance criteria (критерии):**
- Как проверить, что функциональность работает?
- Какие конкретные проверяемые критерии?

**Examples (примеры):**
- Есть ли примеры использования?
- Нужны ли примеры для устранения неоднозначности?

### Для обновления спецификации

Задай вопросы по каждому изменению:

1. **Что изменилось?** — опиши конкретные изменения
2. **Почему изменилось?** — контекст изменения (баг, новое требование, рефакторинг)
3. **Как влияет на текущее поведение?** — текущее vs требуемое
4. **Есть ли противоречия с другими spec?** — проверь связанные спецификации
5. **Нужно ли обновить связанные specs?** — зависимости от других спецификаций

## Workflow

### Шаг 1: Определение scope

1. Определи домен (подкаталог в `specs/`)
2. Определи имя файла → ID спецификации
3. Определи связанные спецификации

### Шаг 2: Уточнение требований

**ЗАДАВАЙ ВОПРОСЫ** по каждому неясному пункту.
Не предполагай — если не уверен, используй `NEEDS_CLARIFICATION`.

### Шаг 3: Написание спецификации

Используй структуру из specs-guidelines:

```yaml
---
last_updated: 2026-10-14
scope: specification
status: DRAFT
---
```

```markdown
# {spec-id}-spec — {Название}

## Purpose
{что и зачем}

## Preconditions
{условия}

## Inputs
{входные данные}

## Behavior
{поведение}

## Business rules
{правила}

## Errors
{ошибки}

## Acceptance criteria
{критерии}

## Examples
{примеры, если нужно}
```

**Правила написания:**
- Описывай **поведение**, а не реализацию
- Используй однозначные формулировки: `должен`, `не должен`, `может`
- Не используй: `обычно`, `как правило`, `по возможности`
- Каждый requirement должен быть проверяемым
- Если поведение неизвестно — `NEEDS_CLARIFICATION`

### Шаг 4: Аудит изменённых/добавленных спецификаций

**Аудит выполняется ДО предоставления результата пользователю.** Все критические замечания должны быть исправлены до показа пользователю.

1. Собери список изменённых/добавленных spec-файлов:
   - При **создании** — новый файл: `specs/{domain}/{spec-id}-spec.md`
   - При **обновлении** — изменённый файл: `specs/{domain}/{spec-id}-spec.md`

2. Запусти суб-агента со скиллом `spec-audit` для аудита этих файлов:

```
task(description="Audit spec: {spec-id}", prompt="Используй скилл spec-audit для аудита спецификации specs/{domain}/{spec-id}-spec.md. Выполни три уровня проверки: код↔spec, тесты↔spec, docs↔code+test. Сфокусируйся только на этом файле.", subagent_type="general")
```

3. Получи результат аудита и проанализируй его:
   - **PASS** — критических замечаний нет, можно предоставлять пользователю
   - **WARN** — есть мелкие расхождения, исправь их самостоятельно
   - **FAIL** — есть критические расхождения, исправь их самостоятельно

4. **Исправь все критические замечания** в spec-файле до показа пользователю.

5. После исправлений — предоставь результат пользователю (см. Шаг 5).

### Шаг 5: Предоставление пользователю

Предоставь:
1. **Готовую спецификацию** — полный текст (с учётом исправлений по результатам аудита)
2. **Результат аудита** — summary от spec-audit, что было проверено
3. **Список уточняющих вопросов** — что было уточнено, что осталось NEEDS_CLARIFICATION
4. **Список допущений** — если что-то было додумано (с пометкой)
5. **Связанные спецификации** — что нужно проверить/обновить

**Все критические замечания из аудита уже исправлены.**
