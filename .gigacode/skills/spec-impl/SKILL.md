# Spec Impl

Реализация или обновление кода в соответствии со спецификацией.

## Правила проекта

**ОБЯЗАТЕЛЬНО** следуй гайдлайнам:
- [`guidelines/implementation-guidelines.md`](../../guidelines/implementation-guidelines.md) — основной гайдлайн реализации
- [`guidelines/specification-guidelines.md`](../../guidelines/specification-guidelines.md) — структура спецификаций, ID, NEEDS_CLARIFICATION
- [`guidelines/documentation-guidelines.md`](../../guidelines/documentation-guidelines.md) — структура docs/, фронтматтер

## Сценарии

### 1. Реализация новой спецификации

```
реализуй спецификацию {spec-name}
```

1. Определи spec-файл: `specs/{domain}/{spec-name}.md`
2. Изучи spec, связанные specs, документацию, текущий код, тесты
3. Определи scope изменений (какие модули затронуты)
4. Реализуй код и тесты
5. Вызови `doc-sync` для обновления документации (используй для этого суб-агента)
6. Вызови `spec-audit` для проверки соответствия (используй для этого суб-агента)
7. Обновить статус спецификации на основе результата аудита
8. Предоставь решение пользователю

### 2. Обновление по изменённой спецификации

```
обнови код по спецификации {spec-name}
```

1. Сравни spec с текущим кодом — определи расхождения
2. Определи минимальные изменения для соответствия
3. Реализуй изменения (код + тесты)
4. Вызови `doc-sync` для обновления документации (используй для этого суб-агента)
5. Вызови `spec-audit` для проверки соответствия (используй для этого суб-агента)
6. Обновить статус спецификации на основе результата аудита
7. Предоставь решение пользователю

## Workflow

### Шаг 1: Изучение

1. Прочитай целевую спецификацию полностью
2. Найди и прочитай связанные спецификации
3. Изучи текущую документацию (`docs/modules/`, `docs/packages/`)
4. Изучи текущую реализацию (код модуля)
5. Изучи существующие тесты
6. Определи различия между spec и текущим кодом

### Шаг 2: Определение scope

Определи:
- Какие файлы кода нужно изменить/создать
- Какие файлы тестов нужно изменить/создать
- Какие модули затронуты
- Есть ли NEEDS_CLARIFICATION — если да, не додумывай, отметь

### Шаг 3: Реализация кода

**Правила:**
- Минимальные изменения — только для выполнения требований spec
- Не меняй поведение, не связанное со spec
- Соблюдай coding standards
- Соблюдай архитектуру модулей (зависимости, паттерны)
- Все исключения — следуй конвенции именования языка/проекта
- Документация на публичных классах/функциях — следуй конвенциям языка/проекта

**Порядок:**
1. Измени существующий код (если нужно)
2. Добавь новые классы/методы (если нужно)
3. Не удаляй код, не связанный со spec

### Шаг 4: Реализация тестов

**Правила:**
- Для каждого значимого требования — тест
- Покрытие: основной сценарий, ограничения, ошибки, граничные случаи
- Не меняй существующие тесты для скрытия регрессии

**Покрытие:**
- ✅ Основной сценарий (Behavior)
- ✅ Бизнес-правила и ограничения
- ✅ Ошибки и исключения (Errors)
- ✅ Граничные случаи

### Шаг 5: Проверка

Перед вызовом downstream skills:
- [ ] Реализация соответствует spec
- [ ] Все значимые требования покрыты тестами
- [ ] Существующие тесты не регрессировали (запусти тесты проекта)
- [ ] Нет известных расхождений между spec, docs и кодом

### Шаг 6: Вызов doc-sync

**ИСПОЛЬЗУЙ ДЛЯ ЭТОГО ШАГА СУБ-АГЕНТА**

После реализации вызови skill `doc-sync` для обновления документации:

```
doc-sync: обнови документацию для модуля {module-name}
```

или для полного обновления:

```
doc-sync: обнови документацию в проекте
```

### Шаг 7: Вызов spec-audit

**ИСПОЛЬЗУЙ ДЛЯ ЭТОГО ШАГА СУБ-АГЕНТА**

После обновления документации вызови skill `spec-audit` для проверки:

```
spec-audit: аудит спецификаций для {spec-name}
```

или для модуля:

```
spec-audit: аудит модуля {module-name}
```

### Шаг 8: Обновление статуса спецификации

На основе результата аудита обновить статус в spec-файле:

| Результат аудита | Новый статус |
|---|---|
| **PASS** | `IMPLEMENTED_STABLE` |
| **WARN / FAIL** | `IMPLEMENTED_NEED_WORK` |

**Правила:**
- Если аудит PASS — измени статус в spec-файле на `IMPLEMENTED_STABLE`
- Если аудит WARN/FAIL — измени статус в spec-файле на `IMPLEMENTED_NEED_WORK`
- Укажи изменения статуса в отчёте

### Шаг 9: Предоставление решения пользователю

Предоставь пользователю:
1. **Список изменений** — какие файлы изменены/созданы/удалены
2. **Результат doc-sync** — что обновлено в документации
3. **Результат spec-audit** — отчёт с статусом (PASS/WARN/FAIL)
4. **NEEDS_CLARIFICATION** — если есть, отметь явно
5. **Рекомендации** — что нужно проверить/уточнить

**Не вноси правки самостоятельно** — предоставь решение пользователю на утверждение.

## Отчёт пользователю

Формат отчёта:

```
## Реализация: {spec-id}

### Статус
- Было: {DRAFT | IMPLEMENTED_STABLE | IMPLEMENTED_NEED_WORK}
- Стало: {DRAFT | IMPLEMENTED_STABLE | IMPLEMENTED_NEED_WORK}

### Изменения кода
- `Path/To/Class.{ext}` — {что изменилось}
- `Path/To/NewClass.{ext}` — {создан}
- `Path/To/Tests.{ext}` — {добавлены тесты}

### Документация (doc-sync)
- `docs/modules/{module}.md` — {что обновлено}
- `docs/packages/{package}.md` — {что обновлено}
- `README.md` — {что обновлено}

### Аудит (spec-audit)
- Статус: {PASS/WARN/FAIL}
- Расхождений код↔spec: {N}
- Непокрытых acceptance criteria: {N}
- Расхождений docs↔code: {N}

### NEEDS_CLARIFICATION
- {если есть — список}

### Рекомендации
- {что проверить, что уточнить}
```

## Критерии завершения

- Реализация соответствует spec
- Все значимые требования покрыты тестами
- Документация обновлена (через doc-sync)
- Аудит пройден (через spec-audit)
- Решение предоставлено пользователю на утверждение
