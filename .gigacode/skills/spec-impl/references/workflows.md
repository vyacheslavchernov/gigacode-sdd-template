# Workflows — Spec Impl

Детальные пошаговые сценарии для реализации спецификаций.

## Промпты для Explore-агентов

### Исследование текущей реализации

```
Исследуй модуль {module-path}/src/{source-dir}.
Мне нужно понять текущую реализацию для аудита по спецификации.
Собери:
1. Все публичные классы/интерфейсы/enum/record/модули (в зависимости от языка)
2. Публичные методы/функции с сигнатурами
3. Иерархию исключений/ошибок
4. Dependency injection / конфигурацию (если есть)
5. Зависимости от других модулей
```

### Исследование текущих тестов

```
Исследуй модуль {module-path}/src/{test-dir}.
Мне нужно понять текущее покрытие тестами.
Собери:
1. Все тестовые классы/файлы и их названия
2. Какие сценарии покрывает каждый тест
3. Какие исключения/ошибки проверяются
4. Есть ли параметризованные тесты / тесты на граничные случаи
```

### Исследование документации

```
Исследуй docs/modules/{module}.md.
Мне нужно понять текущую документацию модуля.
Собери:
1. Описанный публичный API
2. Примеры использования
3. Конфигурация
4. Зависимости
```

## Детальный workflow: Новая реализация

### Шаг 1: Изучение spec

Прочитай spec полностью. Извлеки:
- **Purpose** — зачем нужна функциональность
- **Inputs** — публичный API (классы, методы, параметры)
- **Behavior** — пошаговое поведение
- **Business rules** — ограничения и правила
- **Errors** — исключения и ситуации
- **Acceptance criteria** — проверяемые критерии
- **NEEDS_CLARIFICATION** — если есть, отметь явно

### Шаг 2: Поиск связанных specs

```bash
# Посмотри specs/{domain}/README.md
# Посмотри ссылки в spec на другие файлы
```

Прочитай связанные спецификации — они могут определять:
- Зависимости от других модулей
- Общие паттерны поведения
- Общие бизнес-правила

### Шаг 3: Изучение текущего кода

1. Найди модуль, который будет затронут
2. Изучи структуру пакетов/модулей
3. Изучи существующие классы и паттерны
4. Проверь зависимости в файле сборки (package.json, Cargo.toml, pom.xml, requirements.txt и т.д.)

### Шаг 4: Определение scope

Составь список:
- **Новые файлы** — какие классы нужно создать
- **Изменяемые файлы** — какие классы нужно модифицировать
- **Новые тесты** — какие тесты нужно добавить
- **Изменяемые тесты** — какие тесты нужно обновить

### Шаг 5: Реализация

Следуй порядку:
1. Новые классы/интерфейсы
2. Методы в существующих классах
3. Тесты для нового кода
4. Обновление существующих тестов (если нужно)

### Шаг 6: Проверка сборки

```bash
# Запусти команду сборки проекта (npm run build, cargo build, mvn compile, etc.)
{build-command}
# или для конкретного модуля
{build-command} -m {module-name}
```

### Шаг 7: Проверка тестов

```bash
# Запусти тесты проекта (npm test, cargo test, mvn test, pytest, etc.)
{test-command}
# или для конкретного модуля
{test-command} -m {module-name}
```

### Шаг 8: Вызов doc-sync

**ИСПОЛЬЗУЙ ДЛЯ ЭТОГО ШАГА СУБ-АГЕНТА**

```
doc-sync: обнови документацию для модуля {module-name}
```

### Шаг 9: Вызов spec-audit

**ИСПОЛЬЗУЙ ДЛЯ ЭТОГО ШАГА СУБ-АГЕНТА**

```
spec-audit: аудит спецификаций для {spec-id}
```

### Шаг 10: Формирование отчёта

Собери все результаты и предоставь пользователю.

## Детальный workflow: Обновление по изменённому spec

### Шаг 1: Сравнение spec с текущим кодом

1. Прочитай spec
2. Изучи текущую реализацию
3. Составь таблицу расхождений:

| Spec | Current Code | Action |
|---|---|---|
| Метод X | Реализован | ✅ |
| Метод Y | Не реализован | ➕ Добавить |
| Метод Z | Другое поведение | 🔄 Изменить |
| Исключение A | Не бросается | ➕ Добавить |

### Шаг 2: Минимальные изменения

Для каждого расхождения определи минимальное изменение:
- Добавить метод/класс
- Изменить поведение метода
- Добавить исключение
- Обновить тесты

### Шаг 3: Реализация

Следуй тем же правилам, что и для новой реализации.

### Шаг 4–10: Те же, что для новой реализации

## Чек-лист перед вызовом doc-sync

**ИСПОЛЬЗУЙ ДЛЯ ЭТОГО ШАГА СУБ-АГЕНТА**

- [ ] Код соответствует spec (проверь вручную)
- [ ] Все значимые требования покрыты тестами
- [ ] Тесты проходят (запусти тесты проекта)
- [ ] Сборка проходит (запусти команду сборки)
- [ ] Нет NEEDS_CLARIFICATION (или они отмечены)
- [ ] Нарушения исправлены
- [ ] Соблюдена архитектура модулей

## Чек-лист перед предоставлением решения пользователю

- [ ] Список изменений кода полный
- [ ] Результат doc-sync включён
- [ ] Результат spec-audit включён
- [ ] NEEDS_CLARIFICATION отмечены
- [ ] Рекомендации даны
- [ ] Решение НЕ внесено самостоятельно — ждёт утверждения
